## Purpose

Alembic async migrations, PostGIS bootstrap, and schema evolution for Wandr.

## Requirements

### Requirement: Alembic uses runtime database URL from settings

The migration toolchain MUST read `DATABASE_URL` from `get_settings()` at runtime. The value MUST NOT be hardcoded in `alembic.ini`.

#### Scenario: Env injection on migration run

- **WHEN** an operator runs `alembic upgrade head` with a valid `.env` / environment
- **THEN** Alembic connects using the same async URL as the application (`postgresql+asyncpg://…`)

### Requirement: Alembic supports async SQLAlchemy migrations

The Alembic environment MUST use `async_engine_from_config` with `NullPool` and `connection.run_sync()` so migrations work with the project's async SQLAlchemy stack.

#### Scenario: Online async migration execution

- **WHEN** `alembic upgrade head` runs in online mode (default)
- **THEN** migrations execute via an async engine without blocking the event loop incorrectly and the engine is disposed after completion

### Requirement: geoalchemy2 is registered for autogenerate

`alembic/env.py` MUST import `geoalchemy2` (side-effect registration) so future autogenerated migrations emit correct PostGIS geometry types instead of VARCHAR/Text.

#### Scenario: Geometry type registration

- **WHEN** a developer later adds a model with a `Geometry` column and runs autogenerate
- **THEN** the generated migration references PostGIS geometry types (not plain string columns)

### Requirement: Migration 001 enables PostGIS extensions

Migration revision `001` MUST create PostgreSQL extensions `postgis`, `postgis_topology`, and `uuid-ossp` using `CREATE EXTENSION IF NOT EXISTS`.

#### Scenario: Fresh database upgrade

- **WHEN** `alembic upgrade head` runs against an empty `wandr` database on the PostGIS Docker image
- **THEN** output includes `Running upgrade  -> 001` and all three extensions appear in `\dx`

#### Scenario: Idempotent extension creation

- **WHEN** migration 001 runs on a database where extensions already exist
- **THEN** the upgrade completes without error

### Requirement: Migration downgrade does not drop extensions

Migration 001 downgrade MUST be a no-op. Shared PostgreSQL extensions MUST NOT be dropped on rollback.

#### Scenario: Downgrade safety

- **WHEN** `alembic downgrade base` runs after upgrade
- **THEN** `postgis`, `postgis_topology`, and `uuid-ossp` remain installed

### Requirement: Migrations are not invoked at application startup

The FastAPI application MUST NOT call `alembic upgrade` during lifespan or startup. Migrations are a deploy/CLI concern only.

#### Scenario: App startup without migration side effects

- **WHEN** `uvicorn src.main:app` starts
- **THEN** no Alembic migration commands run automatically

### Requirement: Model imports are registered in alembic env

`alembic/env.py` MUST import each domain `models.py` so autogenerate sees `Base.metadata` tables. New models MUST be added to this import block when created.

#### Scenario: Autogenerate sees registered models

- **WHEN** all implemented models are imported in `env.py` and autogenerate runs
- **THEN** table-creation operations are emitted for those models

### Requirement: Alembic autogenerate template exists

The project SHALL include `alembic/script.py.mako` so `alembic revision --autogenerate` can generate migration files.

#### Scenario: Autogenerate succeeds

- **WHEN** `alembic revision --autogenerate -m "create_all_tables"` runs with all models imported
- **THEN** a new revision file is created without `FileNotFoundError` for script.py.mako

### Requirement: Autogenerate ignores non-application tables

Alembic env SHALL configure `include_object` to skip autogenerate DROP operations for database tables not present in `Base.metadata` (PostGIS/Tiger system tables).

#### Scenario: No spurious DROP operations

- **WHEN** autogenerate runs against PostGIS Docker Postgres
- **THEN** the generated migration contains CREATE operations for application tables only, not DROP of Tiger/geocoder tables

### Requirement: Migration 002 creates six application tables

Migration 002 SHALL create `users`, `destinations`, `places`, `trips`, `trip_places`, `trip_evaluations` with correct types and constraints per step 1.4d review checklist.

#### Scenario: Tables exist after upgrade

- **WHEN** `alembic upgrade head` completes after migration 002
- **THEN** `\dt` lists all six tables and `trip_status` enum type exists

#### Scenario: PostGIS geometry in migration

- **WHEN** migration 002 is reviewed before running
- **THEN** `places.location` uses Geometry type, not VARCHAR or Text

### Requirement: Migration 003 creates trip_edit_events table

Migration 003 SHALL create `trip_edit_events` with `edit_type` PostgreSQL enum and foreign keys: `trip_id` → `trips.id` ON DELETE CASCADE, `place_id` → `places.id` ON DELETE SET NULL.

#### Scenario: Seventh table after upgrade

- **WHEN** `alembic upgrade head` completes after migration 003
- **THEN** `\dt` lists seven application tables including `trip_edit_events`

#### Scenario: edit_type enum exists

- **WHEN** querying `pg_type` for `edit_type`
- **THEN** exactly one row is returned

#### Scenario: Migration is additive only

- **WHEN** migration 003 file is reviewed before apply
- **THEN** it contains no ALTER or DROP on the six existing application tables from migration 002

### Requirement: TripEditEvent registered for autogenerate

`alembic/env.py` MUST import `TripEditEvent` from `src.trips.models` alongside `Trip`, `TripPlace`, and `TripStatus`.

#### Scenario: TripEditEvent registered for autogenerate

- **WHEN** `alembic/env.py` is loaded
- **THEN** `TripEditEvent` is imported from `src.trips.models` alongside `Trip`, `TripPlace`, `TripStatus`
